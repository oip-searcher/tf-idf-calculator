		<div id="mw-content-text" class="mw-body-content"><div class="mw-content-ltr mw-parser-output" lang="ru" dir="ltr"><p><b>Микросервисная архитектура</b>&#160;— вариант <a href="/wiki/%D0%A1%D0%B5%D1%80%D0%B2%D0%B8%D1%81-%D0%BE%D1%80%D0%B8%D0%B5%D0%BD%D1%82%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%BD%D0%B0%D1%8F_%D0%B0%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0" title="Сервис-ориентированная архитектура">сервис-ориентированной архитектуры</a> программного обеспечения, направленный на взаимодействие насколько это возможно небольших, слабо связанных и легко изменяемых модулей&#160;— <i><b>микросервисов</b></i>, получивший распространение в середине 2010-х годов в связи с развитием практик <a href="/wiki/%D0%93%D0%B8%D0%B1%D0%BA%D0%B0%D1%8F_%D1%80%D0%B0%D0%B7%D1%80%D0%B0%D0%B1%D0%BE%D1%82%D0%BA%D0%B0_%D0%BF%D1%80%D0%BE%D0%B3%D1%80%D0%B0%D0%BC%D0%BC%D0%BD%D0%BE%D0%B3%D0%BE_%D0%BE%D0%B1%D0%B5%D1%81%D0%BF%D0%B5%D1%87%D0%B5%D0%BD%D0%B8%D1%8F" class="mw-redirect" title="Гибкая разработка программного обеспечения">гибкой разработки</a> и <a href="/wiki/DevOps" title="DevOps">DevOps</a><sup id="cite&#95;ref-martinfowler&#95;1-0" class="reference"><a href="#cite_note-martinfowler-1"><span class="cite-bracket">&#91;</span>1<span class="cite-bracket">&#93;</span></a></sup><sup id="cite&#95;ref-2" class="reference"><a href="#cite_note-2"><span class="cite-bracket">&#91;</span>2<span class="cite-bracket">&#93;</span></a></sup><sup id="cite&#95;ref-3" class="reference"><a href="#cite_note-3"><span class="cite-bracket">&#91;</span>3<span class="cite-bracket">&#93;</span></a></sup>.
</p><p>Если в традиционных вариантах сервис-ориентированной архитектуры модули могут быть сами по себе достаточно сложными программными системами, а взаимодействие между ними зачастую полагается на стандартизованные тяжеловесные протоколы (такие, как <a href="/wiki/SOAP" title="SOAP">SOAP</a>, <a href="/wiki/XML-RPC" title="XML-RPC">XML-RPC</a>), в микросервисной архитектуре системы выстраиваются из компонентов, выполняющих относительно элементарные функции, и взаимодействующие с использованием экономичных сетевых коммуникационных протоколов (в стиле <a href="/wiki/REST" title="REST">REST</a> с использованием, например, <a href="/wiki/JSON" title="JSON">JSON</a>, <a href="/wiki/Protocol_Buffers" title="Protocol Buffers">Protocol Buffers</a>, <a href="/wiki/Thrift" class="mw-redirect" title="Thrift">Thrift</a>). За счёт повышения гранулярности модулей архитектура нацелена на уменьшение <a href="/wiki/GRASP#5._Высокая_связность_(High_Cohesion)" title="GRASP">связности</a> и увеличение <a href="/wiki/GRASP#4._Слабое_зацепление_(Low_Coupling)" title="GRASP">степени зацепления</a>, что позволяет проще добавлять и изменять функции в системе в любое время<sup id="cite&#95;ref-intorMS&#95;4-0" class="reference"><a href="#cite_note-intorMS-4"><span class="cite-bracket">&#91;</span>4<span class="cite-bracket">&#93;</span></a></sup>.
</p>

<div class="mw-heading mw-heading2"><h2 id="Свойства"><span id=".D0.A1.D0.B2.D0.BE.D0.B9.D1.81.D1.82.D0.B2.D0.B0"></span>Свойства</h2><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=%D0%9C%D0%B8%D0%BA%D1%80%D0%BE%D1%81%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D0%BD%D0%B0%D1%8F_%D0%B0%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0&amp;veaction=edit&amp;section=1" title="Редактировать раздел «Свойства»" class="mw-editsection-visualeditor"><span>править</span></a><span class="mw-editsection-divider"> | </span><a href="/w/index.php?title=%D0%9C%D0%B8%D0%BA%D1%80%D0%BE%D1%81%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D0%BD%D0%B0%D1%8F_%D0%B0%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0&amp;action=edit&amp;section=1" title="Редактировать код раздела «Свойства»"><span>править код</span></a><span class="mw-editsection-bracket">]</span></span></div>
<p>Свойства, характерные для микросервисной архитектуры<sup id="cite&#95;ref-martinfowler&#95;1-1" class="reference"><a href="#cite_note-martinfowler-1"><span class="cite-bracket">&#91;</span>1<span class="cite-bracket">&#93;</span></a></sup>:
</p>
<ul><li>модули можно легко заменить в любое время: акцент на простоту, независимость развёртывания и обновления каждого из микросервисов;</li>
<li>модули организованы вокруг функций: микросервис по возможности выполняет только одну достаточно элементарную функцию;</li>
<li>модули могут быть реализованы с использованием различных <a href="/wiki/%D0%AF%D0%B7%D1%8B%D0%BA_%D0%BF%D1%80%D0%BE%D0%B3%D1%80%D0%B0%D0%BC%D0%BC%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D1%8F" title="Язык программирования">языков программирования</a>, <a href="/wiki/%D0%A4%D1%80%D0%B5%D0%B9%D0%BC%D0%B2%D0%BE%D1%80%D0%BA" title="Фреймворк">фреймворков</a>, <a href="/wiki/%D0%A1%D0%B2%D1%8F%D0%B7%D1%83%D1%8E%D1%89%D0%B5%D0%B5_%D0%BF%D1%80%D0%BE%D0%B3%D1%80%D0%B0%D0%BC%D0%BC%D0%BD%D0%BE%D0%B5_%D0%BE%D0%B1%D0%B5%D1%81%D0%BF%D0%B5%D1%87%D0%B5%D0%BD%D0%B8%D0%B5" title="Связующее программное обеспечение">связующего программного обеспечения</a>, выполняться в различных средах <a href="/wiki/%D0%9A%D0%BE%D0%BD%D1%82%D0%B5%D0%B9%D0%BD%D0%B5%D1%80%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D1%8F_(%D0%B8%D0%BD%D1%84%D0%BE%D1%80%D0%BC%D0%B0%D1%82%D0%B8%D0%BA%D0%B0)" class="mw-redirect" title="Контейнеризация (информатика)">контейнеризации</a>, <a href="/wiki/%D0%92%D0%B8%D1%80%D1%82%D1%83%D0%B0%D0%BB%D0%B8%D0%B7%D0%B0%D1%86%D0%B8%D1%8F" title="Виртуализация">виртуализации</a>, под управлением различных <a href="/wiki/%D0%9E%D0%BF%D0%B5%D1%80%D0%B0%D1%86%D0%B8%D0%BE%D0%BD%D0%BD%D0%B0%D1%8F_%D1%81%D0%B8%D1%81%D1%82%D0%B5%D0%BC%D0%B0" title="Операционная система">операционных систем</a> на различных <a href="/wiki/%D0%90%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0_%D0%BA%D0%BE%D0%BC%D0%BF%D1%8C%D1%8E%D1%82%D0%B5%D1%80%D0%B0" title="Архитектура компьютера">архитектурах</a>: приоритет отдаётся в пользу наибольшей эффективности для каждой конкретной функции, нежели стандартизации средств разработки и исполнения;</li>
<li>архитектура симметричная, а не иерархическая: зависимости между микросервисами одноранговые.</li></ul>
<p>Философия микросервисов фактически копирует <a href="/wiki/%D0%A4%D0%B8%D0%BB%D0%BE%D1%81%D0%BE%D1%84%D0%B8%D1%8F_UNIX" class="mw-redirect" title="Философия UNIX">философию Unix</a>, согласно которой каждая программа должна «делать что-то одно, и делать это хорошо» и взаимодействовать с другими программами простыми средствами: микросервисы минимальны и предназначаются для единственной функции. Основные изменения в связи с этим налагаются на организационную культуру, которая должна включать автоматизацию разработки и тестирования, а также культуру проектирования, от которой требуется предусматривать обход прежних ошибок, исключение по возможности унаследованного кода (микросервисы часто заменяют целиком, поскольку их функции элементарны).
</p><p>Наиболее популярная среда для выполнения микросервисов&#160;— системы управления контейнеризованными приложениями (такие как <a href="/wiki/Kubernetes" title="Kubernetes">Kubernetes</a> и её надстройки <a href="/wiki/OpenShift" title="OpenShift">OpenShift</a> и <span data-interwiki-lang="en" data-interwiki-article="CloudFoundry"><a href="/w/index.php?title=CloudFoundry&amp;action=edit&amp;redlink=1" class="new" title="CloudFoundry (страница отсутствует)">CloudFoundry</a></span><sup class="noprint" style="font-style:normal; font-weight:normal;"><a href="https://en.wikipedia.org/wiki/CloudFoundry" class="extiw" title="en:CloudFoundry"><span title="CloudFoundry — версия статьи «CloudFoundry» на английском языке">[англ.]</span></a></sup>, <a href="/w/index.php?title=Docker_Swarm&amp;action=edit&amp;redlink=1" class="new" title="Docker Swarm (страница отсутствует)">Docker Swarm</a>, <span data-interwiki-lang="en" data-interwiki-article="Apache Mesos"><a href="/w/index.php?title=Apache_Mesos&amp;action=edit&amp;redlink=1" class="new" title="Apache Mesos (страница отсутствует)">Apache Mesos</a></span><sup class="noprint" style="font-style:normal; font-weight:normal;"><a href="https://en.wikipedia.org/wiki/Apache_Mesos" class="extiw" title="en:Apache Mesos"><span title="Apache Mesos — версия статьи «Apache Mesos» на английском языке">[англ.]</span></a></sup>), в этом случае каждый из микросервисов как правило изолируется в отдельный контейнер или небольшую группу контейнеров, доступную по сети другим микросервисам и внешним потребителям, и управляется средой оркестрации, обеспечивающей отказоустойчивость и балансировку нагрузки. Типовой практикой является включение в контур среды выполнения системы <a href="/wiki/%D0%9D%D0%B5%D0%BF%D1%80%D0%B5%D1%80%D1%8B%D0%B2%D0%BD%D0%B0%D1%8F_%D0%B8%D0%BD%D1%82%D0%B5%D0%B3%D1%80%D0%B0%D1%86%D0%B8%D1%8F" title="Непрерывная интеграция">непрерывной интеграции</a>, обеспечивающее автоматизацию обновления и развёртывания микросервисов.
</p>
<div class="mw-heading mw-heading2"><h2 id="История"><span id=".D0.98.D1.81.D1.82.D0.BE.D1.80.D0.B8.D1.8F"></span>История</h2><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=%D0%9C%D0%B8%D0%BA%D1%80%D0%BE%D1%81%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D0%BD%D0%B0%D1%8F_%D0%B0%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0&amp;veaction=edit&amp;section=2" title="Редактировать раздел «История»" class="mw-editsection-visualeditor"><span>править</span></a><span class="mw-editsection-divider"> | </span><a href="/w/index.php?title=%D0%9C%D0%B8%D0%BA%D1%80%D0%BE%D1%81%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D0%BD%D0%B0%D1%8F_%D0%B0%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0&amp;action=edit&amp;section=2" title="Редактировать код раздела «История»"><span>править код</span></a><span class="mw-editsection-bracket">]</span></span></div>
<p>Несмотря на то, что термин «микросервисы» упоминался с середины 2000-х годов, появление концепции относят к ежегодному семинару архитекторов программного обеспечения в Венеции 2011 году. В 2012 году о микросервисах докладывали на конференции 33d Degree в Кракове, а также появился ряд публикаций о «гранулярном SOA», излагающих микросервисный подход. В 2012—2014 годы о внедрении микросервисов в рамках собственных программных разработок заявляли специалисты таких компаний, как <a href="/wiki/Amazon" title="Amazon">Amazon</a>, <a href="/wiki/Netflix" title="Netflix">Netflix</a>, <a href="/wiki/Twitter" class="mw-redirect" title="Twitter">Twitter</a>, с 2015 года в ведущих издательствах регулярно выпускаются книги о микросервисной архитектуре, проводится несколько регулярных конференций, целиком посвящённых микросервисам.
</p>
<div class="mw-heading mw-heading2"><h2 id="Критика"><span id=".D0.9A.D1.80.D0.B8.D1.82.D0.B8.D0.BA.D0.B0"></span>Критика</h2><span class="mw-editsection"><span class="mw-editsection-bracket">[</span><a href="/w/index.php?title=%D0%9C%D0%B8%D0%BA%D1%80%D0%BE%D1%81%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D0%BD%D0%B0%D1%8F_%D0%B0%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0&amp;veaction=edit&amp;section=3" title="Редактировать раздел «Критика»" class="mw-editsection-visualeditor"><span>править</span></a><span class="mw-editsection-divider"> | </span><a href="/w/index.php?title=%D0%9C%D0%B8%D0%BA%D1%80%D0%BE%D1%81%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D0%BD%D0%B0%D1%8F_%D0%B0%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0&amp;action=edit&amp;section=3" title="Редактировать код раздела «Критика»"><span>править код</span></a><span class="mw-editsection-bracket">]</span></span></div>
<p>Архитектура постоянно подвергается критике с самого момента её формирования. Среди новых проблем, которые возникают при её внедрении, отмечаются:
</p>
<ul><li>сетевые задержки<sup id="cite&#95;ref-info1&#95;5-0" class="reference"><a href="#cite_note-info1-5"><span class="cite-bracket">&#91;</span>5<span class="cite-bracket">&#93;</span></a></sup>: если в модулях, выполняющих несколько функций, взаимодействие локально, то микросервисная архитектура накладывает требование атомизации модулей и взаимодействия их по сети;</li>
<li>форматы сообщений<sup id="cite&#95;ref-info1&#95;5-1" class="reference"><a href="#cite_note-info1-5"><span class="cite-bracket">&#91;</span>5<span class="cite-bracket">&#93;</span></a></sup>: отсутствие стандартизации и необходимость согласования форматов обмена фактически для каждой пары взаимодействующих микросервисов приводит как к потенциальным ошибкам, так и сложностям отладки.</li></ul>
